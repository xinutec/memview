# #125 — what the transcript's `cwd` field actually means is not settled

Every relative path this project attributes is resolved against the `cwd` on the
transcript line that carries the call (`agents.rs`, read into
`shell_files::extract`). Two measurements of what that field *is* contradict each
other, and neither is explained.

**It looks like the pre-command directory.** Four consecutive calls, driven by
hand 2026-08-08 and checked against what each printed:

| command | recorded `cwd` | printed |
|---|---|---|
| `cd memcheck` (failed) | `~/Code` | — |
| `pwd` | `~/Code` | `~/Code` |
| `cd memview` | `~/Code` | — |
| `pwd` | `~/Code/memview` | `~/Code/memview` |

**It looks like the post-command directory.** 103 calls in the corpus begin with
a relative `cd X` whose recorded `cwd` *already ends in* `/X`. Under
pre-semantics each would need `…/X/X` to exist. Their own outcomes say
otherwise: **0 of the 103 report a failed `cd`.**

`shell_ops::repeats` reads that shape as a no-op and is therefore right for all
103, and does not fire for any of the four above — so nothing is known to be
broken today. But the rule rests on a model that the first table contradicts,
and the next shape it meets may not be covered by luck.

Candidate explanation, unverified: the line is stamped when it is *written*, and
the transcript is rewritten after the fact
(`reference_claude_transcript_rewrites_history`), so an older line can carry a
later directory. If that is it, the field is not a per-call fact at all and the
resolution wants a different input.

## What was fixed, and is no longer part of this

A `cd` the shell **refused** was applied anyway, so every later relative path in
that script resolved under a directory the command never entered —
`cd memcheck; cat Cargo.toml` recorded `~/Code/memcheck/Cargo.toml` for a file
read at `~/Code/Cargo.toml`. 247 results across this project's transcripts report
one. A verdict cannot carry it (`cd nope; cat x` exits 0), so the shell's own
words are read: `doing::refused_dirs` → `shell_files::extract_knowing`, carried
through the corpus as a `refused` field and into all four reports.

## What is NOT a defect, contrary to this task's first draft

"A path used before a script's first `cd` is credited to the wrong directory" was
demonstrated against a **hand-written** corpus row and judged under the
post-semantics assumption. Under pre-semantics the same row is resolved
correctly, and no real call has been shown to fail this way. Settle the question
above before acting on it.
