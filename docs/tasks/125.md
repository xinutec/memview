# #125 — a path used before a script's first `cd` is credited to the wrong directory

The transcript's `cwd` field is not always the directory a `Bash` call *started*
in. Demonstrated live, 2026-08-08:

    $ cd memview && pwd
    /Users/pippijn/Code/memview

The shell was in `/Users/pippijn/Code` when that ran — that is *why* `cd memview`
succeeded. The transcript stamped the line `/Users/pippijn/Code/memview`: the
directory the command **ended** in.

`shell_files::extract` resolves every relative path in a script against that one
field (`agents.rs:947` reads it; `shell_ops::resolve` joins it). For a script
that changes directory partway, every path named *before* the `cd` is therefore
resolved against a directory it was not read from.

## What the parser already handles

`shell_ops::repeats` (shell_ops.rs:1006) covers the leading case: a relative
`cd X` whose recorded cwd already ends in `/X` is read as a no-op rather than
applied. That rule was measured over 90 calls and is right — it is the same
observation as this task, handled for one shape.

## The shape it does not handle

Probed against `reader --bin shell-files`:

    {"cmd":"cat Cargo.toml && cd frontend && cat package.json",
     "cwd":"/Users/pippijn/Code/memview/frontend"}

    1  0  /Users/pippijn/Code/memview/frontend/Cargo.toml     ← wrong
    1  0  /Users/pippijn/Code/memview/frontend/package.json   ← right

`Cargo.toml` was read at `/Users/pippijn/Code/memview/Cargo.toml`, before the
`cd`. `package.json` is right only because `repeats` neutralised the `cd`.

## The shape underneath it: a `cd` that failed

    {"cmd":"cd memcheck; cat Cargo.toml","cwd":"/Users/pippijn/Code"}
    2  0  /Users/pippijn/Code/memcheck/Cargo.toml

`memcheck` does not exist, so `cat` ran in `/Users/pippijn/Code` and read
`/Users/pippijn/Code/Cargo.toml`. With `&&` instead of `;` the `cat` never ran at
all, and a read is still recorded. **247 tool results across the 14 transcripts
in this project report a failed `cd`** (`cd: … No such file or directory`), each
one a script whose later relative paths resolve under a directory the shell never
entered.

## Where a fix would go

Treat the recorded cwd as the script's **end** state and unwind the `cd` chain
backwards to derive its start, then walk forward as now. `cd <absolute>` resets
the unwind; `cd` with no argument goes home. Done properly this subsumes
`repeats`, which is the same correction applied to one position only.

Two things want measuring before it is written:

- **Is the field reliably the end state?** Counterexamples exist in the corpus —
  a line recording `…/memview/frontend` for a command beginning
  `cd ~/Code/memview && …`, where the end state was `memview`. The harness also
  moves the shell on its own (it prints `Shell cwd was reset to …` after heredoc
  commands and `Session cwd remains …` after backgrounded ones), and the
  transcript is rewritten after the fact. A rule derived from the wrong model
  would move the error rather than remove it.
- **A failed `cd` is not knowable from the text.** The outcome is: the corpus
  already carries `doing::Verdict` per call, and the result text names the
  failure. The honest reading is to poison the directory to `None` from that
  point — which drops relative paths rather than misattributing them, matching
  what `extract` already does when the cwd is unknown.
