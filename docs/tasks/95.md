# #95 — Notice finished background work while the session is mid-tool-call

The count now closes from the transcript rather than from the stream (2026-08-06), but only when the session emits an event: `Session::recount` runs in the task that reads stdout, once per event.

So the residual staleness is the case where a session sits inside one long tool call while a background task finishes. Measured today: the count stayed up for the full three minutes of a blocking loop and dropped to zero the moment the tool returned. It self-heals at the next event and at every turn end, so it is bounded rather than permanent — the earlier defect was not.

The fix is a beat rather than an event: sweep the live sessions whose background set is non-empty and read their transcript tail. Cost is near zero because it does nothing when nothing is outstanding, and the read is incremental from the saved offset.

⚠ **`recount` is not safe to call from a second place as it stands, and its doc says so**: it reads the offset, reads the file, then writes both back, deliberately outside the state lock so that events are not blocked while a file is read. A timer calling it concurrently with the reading task would let both count the same appended bytes and add them twice — and `interactions` is on every card. Give the pair its own mutex, held across the whole read-modify-write and distinct from the state lock, before adding a second caller.

Aligned with #80: a beat is not the request path.
