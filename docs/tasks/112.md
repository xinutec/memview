# #112 — The console calls a working session idle, because a status is only announced when it changes

**Reported from the phone 2026-08-07:** "It says you're idle. My messages aren't seen by you yet." Both halves were true, and the first is a defect — the session was mid-turn throughout, running tools continuously.

**Cause.** `Held.doing()` is fed by `Event::Busy`, which is the CLI's own progress reporting and is **announced when it CHANGES**. A long stretch of one activity, or one the CLI does not narrate, leaves the last announcement standing or nothing standing at all — and no status reads as idle. The same trap is already written down one line away, for questions: *"Nothing is arriving while a question stands, whatever the status says. A status is announced when it CHANGES and asking is not a change."* That fix was scoped to the question case; the general case is this.

**Why it matters more than it looks.** It is what made [[#111]]'s invisible queue actively misleading rather than merely quiet: a message sent to a session the page says is *idle* should land at once, so its not landing reads as a failure. Two wrong signals compounding, and the person on the phone re-sends.

**What "working" actually is.** Not the last narrated activity — whether the turn has ended. The runner sees `Event::Turn` when one finishes and the tool-call traffic while one runs, so it can answer this without asking the CLI to narrate anything. Prefer a fact the runner observes over a status it is told.

⚠ **Do not paper over it with a timeout** ("no status for 30s → assume busy"). The console has had two defects from inferring state on a timer, and a turn can legitimately be quiet for minutes.

⚠ **One of five instances of one defect** — the console reporting its own intent as an outcome. See memory `project_console_reports_intent_not_outcome`; fixing them as a class is cheaper than one at a time, and #120 blocks #121.
