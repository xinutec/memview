# #121 — The console should name a deaf session instead of saying "waiting to be read" for ever

A session can stop reading its stdin while alive (see `reference_console_session_stops_reading_stdin`). Today the `hardware` session did it **twice in 75 minutes** — 08:47 and 09:37 local, after 18 and 26 minutes of work. The console said *waiting to be read* both times, which is what it also says about a message a busy session will get to in a minute. The two are indistinguishable on screen, so every occurrence costs a manual diagnosis.

## The console already holds the read receipt

The runner spawns the CLI with **`--replay-user-messages`**. The CLI echoes each user message back when it *reads* it, and that echo is what `fold()` uses to clear the queued marker. So:

- `Event::Accepted` = the bytes reached the pipe.
- The replay = the session actually read them.

An accept with no replay is the definition of deaf. Nothing new needs measuring.

⚠ **This holds for a prompt and only for a prompt.** Measured 2026-08-08: `--replay-user-messages` does not replay a slash command. Since #120 that is structural rather than a caveat to remember — the runner sends `Event::Command` for a command and `Event::Accepted` only for something a receipt can come back for, so an alarm keyed on an unanswered `Accepted` cannot fire on a command.

## What to build

When a message has been accepted, no replay has come back for N seconds, and no turn is running (last transcript line is `end_turn`, transcript mtime not advancing), the session is deaf. Say so on the card and in the session, and offer a one-tap **restart** — stop, resume, re-send the unread messages, which is exactly the manual sequence and the only known cure.

N wants measuring, not guessing: the legitimate wait is a turn ending, which is bounded by the transcript still growing. Both real episodes were silent for 20+ minutes.

## The silence that is NOT deafness

~~A slash command.~~ Settled by #120: a command is now its own event and is never marked as waiting, so it cannot raise this alarm.

⚠ **A compaction in progress**, and this one is still live. `/compact` is a long legitimate silence with *no transcript growth at all* — measured 2026-08-08 09:51 on `hardware`: sent at 09:50:46, transcript still frozen at 09:49:53 twenty seconds later, and it stays frozen for minutes while a 437k-token context is summarised. So mtime is not a pulse during compaction, and an ordinary message sent *while* one is running is a genuine `Accepted` with no receipt and a dead transcript — deafness by every test this task proposes.

#120 left the handle for it: the runner sees the `/compact` go by as an `Event::Command`, so it knows a compaction is outstanding and can hold the alarm until the summary lands. What ends the suppression wants deciding — the `compacted` event is the obvious candidate.

## Capture before curing

A restart destroys the evidence, and it has now destroyed it twice. Before resuming, dump `sample <pid> 10`, `lsof -p <pid>`, and the transcript tail to a file under the session dir. A third episode should then be comparable to the first two instead of re-derived by hand.

The 09:37 episode was captured by hand at `scratchpad/deaf-2026-08-08T0937/` — sample, lsof, ps, transcript tail, runner log. From it: **fd 0 was still an open PIPE with a 16 KB buffer**, so nothing had closed or broken; the process simply was not draining it.

## What is already ruled out

- `U`/`UN` process state — a healthy session sits in `UN` too.
- Transcript size — a 467 MB session was fine, a 55 MB one stuck.
- **Queued input.** Both freezes followed `queue-operation` entries, but so did four episodes today that did *not* freeze, and `dev-lint` had 14 overnight while staying healthy. Correlation refuted.
- CPU state: the deaf process burns a flat ~5% (measured +2.42 s per 45 s, twice running) — an idle loop, not work.

Root cause still needs `fs_usage`/`dtruss` to see whether stdin is still in its kqueue, which needs root. This task deliberately does not wait for that: detection and cure are useful without it.

⚠ **One of five instances of one defect** — the console reporting its own intent as an outcome. See memory `project_console_reports_intent_not_outcome`; fixing them as a class is cheaper than one at a time. #120 is done and this is no longer blocked.
