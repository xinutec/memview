# #117 — A waiting message sits above work that happened before it was read

**Found by Pippijn from the phone, 2026-08-07**, within an hour of the queued-message marker shipping — and it is a defect that marker introduced.

`Event::Accepted` puts the message in the transcript when the *runner* takes it. The CLI may not read it for minutes (see #111 for the measurements), and everything the session does in between is appended **below** it. So the transcript reads as though the message was seen and then the work continued, when every one of those entries predates the session reading a word of it. His words: *"It'll end up somewhere out of sync with what you actually see."*

**Both timestamps are real and they answer different questions.** When it was *sent* is the sender's fact and belongs to them; when it was *read* is where it enters the conversation. Rendering only the first is what makes the order a claim about causality that is false.

**Shape of the fix.** Keep the entry where it was sent *while it waits* — that is the sender's own timeline, and it is what stops the re-sending #111 exists to prevent. On the echo, **move it to the current end** instead of clearing the flag in place (`transcript.ts`, the `prompt` case). The jump is the information: above it is what happened before it was read, below it is what happened after.

⚠ **Not simply "insert it at the end when read"** — then a waiting message would appear nowhere until read, which is exactly the invisibility #111 removed.

⚠ **The move must survive two identical messages.** #111 already answers the oldest waiting copy by text; the move must take the same entry, not the newest match. There is a test for the matching in `transcript.spec.ts`; extend it rather than writing a second one.

⚠ **Check what it does to following** (#116): moving an entry changes `scrollHeight` under a reader, which is the class of event that whole module is careful about.

⚠ **One of five instances of one defect** — the console reporting its own intent as an outcome. See memory `project_console_reports_intent_not_outcome`; fixing them as a class is cheaper than one at a time, and #120 blocks #121.
