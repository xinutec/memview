# #106 — Typing /tasks in the console does nothing

`/tasks` typed into the console produces no task list.

**The data is already there and already served.** `console/src/tasks.rs` reads `~/.claude/tasks/<session-id>/<n>.json` straight off disk — no control request, so a session busy for ten minutes answers instantly and one that has exited answers at all — and `api.rs` exposes it on two routes: `/api/sessions/{id}/tasks` for the list and `/api/sessions/{id}/tasks/{task}` for one task's prose, split because 355 tasks of written-up description are 1.5 MB and a list does not need them. So this is not missing a reader; it is missing the path from what gets typed to the reader that exists.

**Measured 2026-08-08, and candidate 1 below is refuted.** The CLI *does* execute slash commands when driven with `--input-format stream-json`: `/context` written to a session's stdin came back as a complete `assistant` message carrying the whole context table. So the command runs, and the answer reaches the console's own reader.

**It is thrown away one step later, and not only for `/tasks`.** That reply has `"model": "<synthetic>"` and arrives whole — no `content_block_delta` precedes it, because nothing was generated. The live reader (`protocol.rs`, `Line::Assistant`) keeps only `Block::ToolUse` from a completed message and drops its text, on the sound rule that the deltas already carried it. For a synthetic message there were no deltas, so the rule silently discards the entire output of **every slash command**. `/context`, `/status`, `/model` are all equally invisible; `/tasks` is just the one that got noticed.

So the narrow fix is one condition in the live reader: keep the text of a message whose model is `<synthetic>`. That is a repair to a rule that is wrong about a case it never met, and it makes every command's answer visible at once.

**The remaining choice is only about `/tasks` specifically:**

1. Let it run in the session and render the reply, now that the reply survives. Costs the session a turn's context, and needs the session alive.
2. The console recognises `/tasks` itself and answers from its own reader without involving the session. Instant, works on an exited session, costs no context.

The second is still the better one for this command, and the two do not conflict — the reader fix is worth doing regardless, since it is every other command's only route to the screen.

**Decide the surface with it:** a task list is a list with state, not a paragraph. If it comes back as prose in the conversation it will be unreadable at forty items on a phone; the console already draws cards for other structured things and this should be one of them.
