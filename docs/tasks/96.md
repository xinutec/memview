# #96 — The mode on the card should be the session's, not the one we asked for

Found 2026-08-06. `Session::set_mode` writes a `set_permission_mode` control request to stdin and records the new mode immediately, without waiting for the answer — documented in the code as a deliberate trade so a client is not frozen behind a busy session.

The cost showed up today. A switch to `bypassPermissions` was asked for and the header duly read Bypass Permissions, while the CLI stayed in `auto` and went on asking for approval — its own `{"type":"permission-mode","permissionMode":"auto"}` line in the transcript is the evidence. Nothing recorded a refusal, because the `control_response` that answers this request goes nowhere: `protocol` reads control responses only for rate limits.

So the console showed a session as unrestricted while it was anything but. That is the wrong direction to be wrong in — the same failure the mode display exists to prevent, and the reason `modeIsLoud` flags bypass at all.

The fix is to match the response on its `request_id` — `set-mode-{session}` is already unique — and either confirm the mode or surface the refusal in the words the CLI used. Optimism can stay for the moment between asking and hearing back; what cannot stay is a claim that is never corrected.

Also worth checking while there: whether the CLI refuses `bypassPermissions` at runtime as a rule (it is normally a startup flag with its own guard), because if so the honest UI is to offer it only when starting a session, not on a running one.

⚠ **One of five instances of one defect** — the console reporting its own intent as an outcome. See memory `project_console_reports_intent_not_outcome`; fixing them as a class is cheaper than one at a time, and #120 blocks #121.
