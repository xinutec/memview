# #110 — Nothing watches the boot disk, and nix deletes store paths mid-build before it fills

LOW PRIORITY — filed 2026-08-07 from a failure it would have explained.

Sibling of #103. `claude_disk.py` grades the volume `~/.claude` lives on and deliberately said nothing about the boot disk. But the boot disk is what hosts `/nix/store`, the 58 GB cargo target dir and `/private/tmp`, and it is the one that broke two gate rows today.

## ⚠ RAISED 2026-08-08: `~/.claude` moved ONTO the boot disk

The half of this about *watching* the boot disk is now incidentally done — `claude_disk.py` follows `~/.claude` and therefore grades the boot disk, in days of headroom. What it grades against is still the volume running out, **not** the `min-free` cliff below, so the interesting number is still missing.

And the priority is the wrong way round from what "LOW PRIORITY" says, because the two contributors are now the same disk:

- Before the move, the corpus growing 0.5 GB/day was harmless to builds — different hardware.
- Now it eats the very headroom that keeps nix from deleting store paths mid-build. Measured against nix's own config (`min-free = 21474836480`), not an estimate: 45.7 GB free minus a 21.5 GB floor is **24.2 GB of usable room** — and `~/.claude` is 6.9 GB of what has already been spent, growing.

So the corpus-growth work and this check are one problem now, not two.

## The threshold is a known constant, not a judgement

`/etc/nix/nix.conf`, confirmed against `nix config show`:

    min-free = 21474836480          # 20 GiB — below this, nix DELETES store paths
    max-free = 64424509440          # 60 GiB — it keeps deleting until it reaches this
    min-free-check-interval = 5     # seconds, checked DURING builds

So the interesting quantity is headroom against **20 GiB**, never a percentage.

## Why it matters more than "the disk is full"

Crossing `min-free` does not fail the disk — it corrupts running builds. Observed today: free space reached ~19.7 GiB, nix set out to reclaim up to `max-free` (40.3 GiB, matching the log's `running auto-GC to free 43247640576 bytes` to the byte) and deleted `pnpm-11.17.0.drv` while a build held it. The memview gate failed 2/13 with:

    ng-build: cannot run pnpm: No such file or directory (os error 2)
    error: store path '/nix/store/...-pnpm-11.17.0.drv' does not exist

There is no "no space left on device" anywhere in that. It reads as a toolchain fault, and my first diagnosis was wrong because of it. **The check's `observed` should name that symptom** — that is most of its value.

## What to build

Reuse everything #103 already has: rolling samples in the state file, `headroom_days` from the rate free space is *falling*, `headroom_verdict`. Add a second headroom check for the boot disk, expressed as **days until nix starts deleting things mid-build** — free space above `min-free`, over the fall rate.

- **Read `min-free` from nix's own config**, do not hardcode 20 GiB. Raising it moves the cliff, and a check carrying its own copy would then be wrong rather than merely coarse. `nix config show | grep '^min-free'`.
- The check is now called `on the boot disk with home` and its expectation inverted with the move: it compares `CLAUDE.stat().st_dev` against `HOME`'s and fails when they DIFFER. Both devices are known to the collector either way — but they are now the same one, so the boot-disk headroom check is no longer a *second* volume to reach for. It is a second *threshold* on the volume already being graded: the volume emptying, and `min-free` being crossed, are different distances on the same line.

## A second line, ungraded: /private/tmp

36 GB today and the fastest-moving contributor. **It must not be swept and must not be implied to be sweepable** — the largest single item was a live session's 20 GB workspace, and I nearly deleted it (see [[reference_lsof_on_a_directory_misses_what_is_open_inside]]). macOS already handles the disposable part correctly: `com.apple.tmp_cleaner` runs daily at 00:00 and deletes anything with atime, mtime AND ctime older than 3 days. So report size and the age of the oldest orphan; grade nothing. A reboot is NOT the lever — macOS has not cleared /tmp at boot for years.

Was "not urgent" when the disk sat at 73 GB free, well clear of the cliff. **It is 42.6 GB now** — the move cost 6.9 GB and the rest went elsewhere — so the margin above `min-free` has roughly halved, and a third contributor (the corpus) has joined the cargo target dir and `/tmp` on the same disk. The shape that produced today's failure is closer, not further away.
