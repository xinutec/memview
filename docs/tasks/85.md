# #85 — Read the branch a conversation is on, not the file it is in

A transcript is not a log — the CLI rewrites stretches of history back into the same file, and the console replays every copy as fresh material.

Measured 2026-08-06 on the health session (296dae53, 2.7 GB): 216,019 lines carry a uuid, 155,930 of them distinct. 60,089 lines — 27.8% — are a second or later copy of a line already in the file. 9,428 uuids appear more than once. Two "What's next?" prompts from 5 August (13:10 and 13:37) sit at 2.383 GB and again, byte-identical with the same uuids and the same replies after them, at 2.695 GB — 312 MB apart.

What that costs: scrolling back through a long conversation reads the same stretch twice with no sign it is a repeat, and every walk over the file (#80, the gist material, the task sweep) pays for a quarter more bytes than the conversation contains.

The structure that would fix it is already in every line: parentUuid. The conversation is a chain from the newest leaf backwards, and every line off that chain is an abandoned branch or a rewritten copy. Reading the chain gives each message once and drops the dead branches for free.

The open question is how to walk it backwards in a 2.7 GB file without an index — which is the same question #83 asks, so the two should be answered together. Cheap first step worth measuring: within one replay page, are the duplicates ever adjacent (per-page dedup by uuid would be nearly free), or are they always far apart as the pair above suggests?
