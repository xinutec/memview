# #124 — console-live grows for ever — nothing prunes the superseded bundles

`frontend/dist/console-live` is what the running console serves (`STATIC_DIR`, set in `scripts/console-service.sh` and `scripts/console.sh`). It is filled by `build:console`:

    ng build console-web && rsync -a dist/console-build/browser/ dist/console-live/ && …

**`rsync` without `--delete`, on purpose.** `ng build` empties its own output directory first, so serving straight from the build output means a page loading mid-build asks for a font and is handed HTML. Copying into a second directory that is never emptied is what makes an upgrade invisible to whoever is looking at the console while it happens.

Bundle names carry a content hash, so every build adds a new set and none is ever removed. Measured 2026-08-08: **107 MB across 172 files**, of which one `main-*.js` is current.

## Why it cannot simply delete the old ones

A phone that has the app open is running a bundle that the next build supersedes, and it goes on asking for that bundle's chunks — lazy routes, fonts — until it reloads. Deleting on build is how a session in someone's hand breaks halfway through a tap. #115 is the same fact seen from the other side: going back restores the pre-update page and it is still running the old bundle.

So the rule wants to be an age or a generation count, not a sweep: keep the current set and enough behind it that a client which has not reloaded still finds what it asks for. What "enough" is wants measuring against how long a phone actually holds a page open, rather than guessing.

## Where it should live

`build:console` is the only writer, so pruning belongs beside the `rsync` — one step that keeps the last N generations. `index.html` names the current entry point, which is what tells a pruner which generation is current without parsing anything.
