# #111 — A message the runner has taken but the session has not read should say so

**Measured 2026-08-07, from the phone.** Messages sent while a session is mid-turn are accepted by the runner instantly and shown to the model **up to twelve minutes later**. The console gives no sign of the gap, so the sender reasonably concludes nothing arrived and sends again — three duplicates in one evening, twice the same sentence and twice "Hi".

**Where the time goes, hop by hop, all of it evidenced:**
- **Phone → runner is instant.** `api::input` writes to the session's stdin and flushes on the spot; it logs `accepted N characters to send` per message. Two deliberate test messages logged at `20:03:30`/`20:06:10` for a 21:03/21:06 send — exact.
- **The CLI parks them.** They land in the transcript as `attachment: {"type":"queued_command"}`, and every one of a batch carries the *same* transcript timestamp — because that timestamp is the release, not the arrival. Four messages accepted at 19:46:07, 19:46:22, 19:53:57 and 19:55:07 were released together at **19:57:59**.
- **Between turns it is seconds**, measured three times in a row: 24s, 6s. So the queue is the whole of the delay and nothing else is broken.

**The fix is the console's, not the CLI's.** The runner already knows both facts: that it accepted the text, and that the CLI has read it — the latter arrives as `Event::Prompt`, the `--replay-user-messages` echo, which is exactly the "difference between sent and received" the protocol doc describes. Today the transcript entry appears only on the echo, so an accepted-but-unread message is invisible.

Show it: put the message in the transcript when the runner accepts it, marked **queued — the session is mid-turn**, and promote it when the echo arrives. ⚠ Match the echo to the message rather than assuming order or a single outstanding one: two 71-character sends fifteen seconds apart is a real shape from this evening, and a length is not an identity.

⚠ **Do not "fix" this by holding the send until the session is idle.** The runner delivering immediately is correct — the message is safe in the CLI's queue the moment it is written. What is wrong is only that nobody says so.

⚠ **One of five instances of one defect** — the console reporting its own intent as an outcome. See memory `project_console_reports_intent_not_outcome`; fixing them as a class is cheaper than one at a time, and #120 blocks #121.
