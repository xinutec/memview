# #116 — Following oscillates: it unpins every 10-25 seconds and stops catching up

⚠ **This task's first description was WRONG and is corrected here.** It said the reader had been unpinned once by a stray five pixels, and proposed widening the threshold or measuring scroll direction. A fix was written to that theory, ablated, and **all 162 tests still passed with the fix removed** — the new cases never reached the added code, because the engine's existing `wrote` guard short-circuits them. Reverted, uncommitted. Recording the wrong turning as well as the right one: the theory was arrived at by reading source, and the data was available the whole time.

**What the console's own client telemetry actually shows** (2026-08-07, phone):

    gap=19 top=16202 height=16830 view=609 entries=170
    gap=20 top=17100 height=17726 view=606 entries=172
    gap=18 top=17792 height=18419 view=609 entries=175
    gap=26 top=17982 height=18617 view=609 entries=177
    gap=17 top=18789 height=19415 view=609 entries=179
    gap=16 top=19086 height=19711 view=609 entries=182
    gap=18 top=19490 height=20117 view=609 entries=184

Two facts change everything:
1. **`top` climbs with `height`.** The view *is* tracking the bottom. This is not a reader who scrolled away and was abandoned.
2. **`unpinned` is logged only on the pinned → unpinned transition** (`session-view.ts`: `if (followed && !this.following.pinned)`). So these are **ten separate unpins**, one every 10-25 seconds. It re-pins in between and does it again.

So the defect is an **oscillation**, not a one-way trip. Each cycle: write to the bottom → more content renders → the gap re-opens at 16-26px → a scroll event arrives → `atEnd` is false against `SLACK = 16` → unpin → following stops → something re-pins → repeat. The reader sees the unpinned half as a page that has died, while entries keep arriving below the fold.

**The open question, and why it is open.** `Following.moved` already refuses to unpin on a scroll carrying the position it last wrote — `if (this.at && box.top === this.wrote) return` — which is precisely this race, and it is evidently not catching these. Three explanations remain and they are indistinguishable from outside: the position does not match exactly (fractional `scrollTop`, or a second render between write and event); a finger was down; or something moves the view that is neither the reader nor the engine.

**Instrumented rather than guessed at again.** The unpin trace now carries `was=` (previous position, which gives direction), `wrote=` (what the engine last wrote, which identifies its own writes) and `held=` (finger down). One session of ordinary reading settles which of the three it is.

⚠ **Do not raise `SLACK` to cover the residue.** `following.ts` has already paid for numbers tuned until green — 120px arriving, 300px leaving, "I need to scroll up quite a lot, then it won't do that" — and the residue has a cause worth knowing. The threshold is not the bug; whatever re-opens the gap after every write is.

⚠ **And do not simply re-pin when the gap is small**: that is the defect #82 exists to prevent, yanking somebody who is deliberately reading back.
