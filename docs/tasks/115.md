# #115 — Going back restores the pre-update page, still running the old bundle

**Reported from the phone 2026-08-07, straight after a deploy:** a left-swipe back lands on the previous version of the app.

**Cause.** `Updates` compares a bundle fingerprint on every `/api/state` and calls `document.location.reload()`. A reload replaces the *current* history entry's document — but every entry created before it still belongs to the **old** document, which the browser keeps alive in the back/forward cache. Going back resurrects that page: not stale HTML, a live old bundle. The console pushes history entries of its own for every sheet (`Dismiss.onBack`), so there are usually several to land on.

**And then it deliberately stays there.** The restored page notices within one poll that its fingerprint is behind, and the timing rule sends it to `pending` rather than reloading: *visible and mid-session → hold until the app is next put away*. That rule is right for a page somebody has been sitting on with a half-typed instruction in it, and wrong for one they have just navigated back into.

**Fix:** treat a restored page as a boot. On `pageshow` with `event.persisted === true`, reset `booted` — so the existing STARTUP_MS branch reloads it at once if it is stale, and does nothing at all if it is not. Small, and it reuses the decision already there rather than adding a second one.

⚠ **Watch the interaction with #89** (a half-typed message does not survive leaving the chat). Reloading a restored page cannot lose a draft that leaving already lost — but if #89 lands first, this must not undo it: restore the draft, then reload, or hold for the same reason the mid-session rule holds.
