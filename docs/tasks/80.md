# #80 — Stop walking every transcript on the request path

Three call sites read whole transcripts synchronously while serving a request. The corpus is 4.0 GB across 13 files; the largest is 2.1 GB / 267,002 lines and takes 24 seconds to read raw. `past::counted` was already made incremental for this reason (it reads forward from a stored byte offset and carries the offset across an upgrade), but the remaining walks have not been.

Two separate problems, and they need separating before either is fixed:

1. THE WALKS THEMSELVES. Find the three sites and establish for each whether it can read a tail, resume from an offset, or must read whole. A tail read is already the pattern for names and context (`TAIL_BYTES` = 128 kB in `past.rs`).

2. `/api/state` DOES FILE I/O ON THE ASYNC EXECUTOR. It is `async fn` but reads the filesystem synchronously, so a slow read blocks a tokio worker rather than yielding — which on a machine with 13 live sessions is a stall everybody shares. `spawn_blocking` is the fix, but it is worth measuring first: with warm page cache the reads may be fast enough that the executor never notices, and adding a thread hop to a hot path on no evidence is the wrong trade.

MEASURE BEFORE CHANGING. The front page polls every 5 s from a phone; if this were costing anything it would show as a slow `/api/state`, and nothing has reported one. Do not assume the cost is real because the file sizes are alarming.
