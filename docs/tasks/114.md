# #114 — curl -o writes a file and nobody is credited with it

**Found by reading a parse on the phone 2026-08-07** — the view's first day of work, and the first thing it turned up.

`curl` sits in `shell_ops`'s `Verb::Nothing` list, under "another machine's filesystem, whatever the operands look like", beside `ssh`, `sftp`, `rclone` and `wget`. Right for `curl URL`, wrong for `curl -o /tmp/x.json URL`, which writes a local file the index then attributes to nobody.

**Measured on the 2026-08-07 corpus: 335 of 1,223 curl/wget calls — 27% — carry `-o`, `-O` or `--output`.**

⚠ **The asymmetry is the tell.** `curl URL > file` **is** counted, because a redirect is collected separately from whatever the command is, while `curl -o file URL` is not. The same shape as the `sed -e` defect already in the record: *a script given by a FLAG leaves no operand to skip* — here, an output given by a flag leaves no operand to notice. Two spellings of one act, counted differently, which is the failure mode this table exists to avoid.

**Shape of the fix:** `curl`/`wget` stop being `Nothing` and become a verb that writes the value of `-o`/`--output` (curl) or `-O`/`--output-document` (wget) and reads nothing else. ⚠ `curl -O` is **not** `wget -O`: curl's takes no value and names the file after the URL's last segment, which this reader cannot resolve and must therefore refuse rather than guess. Everything else about them stays `Nothing` — a URL is not a path, and the remote side is not this machine's.

---

## STATE 2026-08-08: implemented, measured, NOT committed

`reader/src/shell_ops.rs` and `reader/tests/shell_files.rs` are **modified in the working tree** and deliberately not committed. `Verb::Fetch { writes: &'static [&'static str] }` is added, `curl`/`wget` are removed from the `NoFiles` alternation, and `Fetch` lowers to `Op::Write { paths: paths(&flag_values(argv, writes), cwd, home) }`.

**Ablated properly** — baseline restored by `git checkout` and re-run, which reproduced the old numbers exactly:

| | reads | writes |
|---|---|---|
| baseline | 204,720 | 32,652 |
| with `Verb::Fetch` | 204,70**1** | 33,0**23** |

**+371 writes**, close to the 335 predicted, and curl now carries 494 writes. That half is as designed.

⚠ **BLOCKER: reads fell by 19 and I cannot explain it.** Nothing in the change should be able to remove a read. I copied the modified file aside, `git checkout`ed it, re-ran to confirm the baseline, and diffed to prove only the intended lines moved (the `Fetch` variant, the curl/wget arms, the `NoFiles` removal, the classify arm). The diff contains nothing that touches a read path.

**This does not land until the −19 is accounted for.** Either it is a real second defect the change happens to correct (in which case say which, and it deserves its own line in the record), or the measurement is not measuring what it claims.

Note `cargo fmt -p reader` has been run over both files, so the tree is gate-clean apart from being uncommitted.
